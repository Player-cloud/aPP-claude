# Architecture Decision Log

Each decision records status, alternatives and trade-offs (ROADMAP Phase 0 exit criterion). **Proposed** decisions are defaults the code currently follows; they are not final until approved.

| ID | Decision | Status | Alternatives considered | Trade-off / reason |
|---|---|---|---|---|
| DEC-001 | App shell: **Electron**, Windows 10/11 x64 first (NSIS installer) | **Approved 2026-10-27** (decision card) | Tauri + Node sidecar; local web app first | Core and Claude Agent SDK are Node; Electron needs no sidecar. Costs: ~100 MB installer, higher memory. |
| DEC-002 | Core language: **TypeScript on Node ≥ 22.18**, run directly via Node type stripping (no build step for core/CLI) | Adopted for M1 (low risk) | Python core; compiled TS | One language across core, CLI, UI, Agent SDK. Erasable-only TS syntax required (`erasableSyntaxOnly`). |
| DEC-003 | Storage: **SQLite** via built-in `node:sqlite`, one file in the app data dir; artifacts as plain files per project | Adopted for M1 (behind `Workspace`) | `better-sqlite3`; JSON files; Postgres | No native build, transactional, easy backup. `node:sqlite` is experimental in Node 22; swap to `better-sqlite3` if its API shifts. |
| DEC-004 | `blocked` is **resumable** to the state it was blocked from; `completed`/`cancelled`/`failed` are terminal | Adopted for M1 | Treat `blocked` as terminal (as ARCH §4 lists it) | FR-APP-004 requires a blocked run to explain how to resolve the blocker, which implies resumption. ARCH §4 should be updated to match once approved. |
| DEC-005 | Execution: **local**; one directory per project; Git worktrees for isolated changes | **Approved 2026-10-27** (bundled in DEC-001 card) | Remote sandbox; hybrid | Keeps source local; sandbox design still required before running untrusted code (M3). |
| DEC-006 | Secrets: OS credential store via Electron `safeStorage`; DB stores references only; redaction at storage boundary as a safety net | Redaction adopted; store proposed | Encrypted file; external vault | FR-SEC-002. |
| DEC-007 | Single local user for v1; approvals recorded as audit events with the OS username as actor | **Approved 2026-10-27** (bundled in DEC-001 card) | Multi-user with accounts | Nothing in the spec requires multi-user yet. |
| DEC-008 | Model runtime: **Claude via Claude Agent SDK** | **Approved 2026-10-27** (bundled in DEC-001 card) | Direct Messages API; multi-provider | Reuses Claude Code skills/plugins/MCP the Tool Registry depends on. |
| DEC-009 | Audit log is append-only, enforced by database triggers | Adopted | App-level only | Defence against accidental edits (ARCH §7). Not tamper-proof against someone with file access; formal protection is "later enterprise hardening". |
| DEC-010 | Roadmap reorder: read-only tool inventory (FR-TOOL-001/002) right after Phase 2; import/assessment (Phase 7) before design (Phase 5) | Proposed | Follow roadmap order exactly | Phases 3 and 6 need verified tool inventory; assessment is read-only and independent of UI. Scope and exit criteria unchanged. |
| DEC-011 | UI: **React 18** rendered in a sandboxed Electron window; main, preload and renderer bundled with **esbuild** | Adopted for M2 | Vanilla DOM; Vite; Vue/Svelte | React is the most widely known UI library for a multi-screen app; esbuild is one dev dependency with no config. Core and CLI still run unbundled on Node. |
| DEC-012 | Installer: **electron-builder NSIS**, per-user install, user can choose folder; uninstall keeps user data | Adopted for M2 | MSI; Squirrel; MSIX | Simple per-user install without admin rights. **Unsigned** until a code-signing certificate exists, so SmartScreen warns. Auto-update deferred (D10). |
| DEC-013 | Phase 1 items *credential references* and *basic integration registry* move to M4 (tool inventory) | Proposed | Build them in M2 | No connector exists yet to store credentials for; building the registry with the inventory avoids two sources of truth (ARCH §3.11). |
| DEC-014 | Electron **45** (Node 24.22), whose built-in `node:sqlite` was verified to work | Adopted for M2 | Older Electron + `better-sqlite3` | No native module rebuilds. Verified by the e2e suite and the installer smoke test. |
| DEC-016 | **M4 is read-only.** The tool inventory reads Claude Code's documented locations (see OPERATIONS) and never starts MCP servers, runs hooks, or edits or removes anything. Findings are classified as overlap, potential, confirmed or release-blocking, with evidence kept separate from inference. Removal (FR-TOOL-004) stays in Phase 10b and needs its own approval | Adopted (joshua chose M4, 2026-10-27) | Start servers to list their tools; offer one-click removal now | Reading never risks the user's global setup. Without starting servers, duplicate MCP tool names cannot be detected, and the report says so. Locations not confirmed on a real Windows machine yet: the managed-settings folders and `CLAUDE_CONFIG_DIR/.claude.json`. |
| DEC-015 | **Frosted-glass visual style** (translucent blurred panels over a gradient backdrop) in dark and light themes, with a *Solid panels* setting. Layout follows joshua's six reference designs: graphite palette with violet/teal glow, slim icon rail with tooltips, a context panel (project explorer with search and tree lines), a prompt-style composer, project cards and run cards with progress bars | Adopted at joshua's request (2026-10-27) | Flat opaque surfaces (M2 look) | Blur only on large panels to limit GPU cost; solid fallback when the setting is off or the OS asks for reduced transparency, which also helps readability. |
| DEC-017 | **M3 orchestrator with a simulated model only.** No real model calls until joshua sets a monthly budget. The orchestrator is deterministic code: the model only proposes a plan (validated as untrusted JSON); strategy, budget, timeouts, permissions, output checks and reconciliation are enforced in code. Strategy rules: one subtask, overlapping writes, or all subtasks small → single agent; three or more independent large subtasks, none high risk, affordable at ~1.5× → team; otherwise sequential subagents. A `budget` setting (`none`/20/50/100 USD a month, default `none`) gates billable calls, and spend goes to an append-only ledger. Delegated tasks get no tools from the UI, and tool execution is not built yet (requested tools are only checked against the allow-list) | Adopted (joshua chose "No real calls yet", 2026-10-27) | Wire the Claude Agent SDK now with a cap | No cost or credential risk while the workflow is proven. The simulated output is labelled in the CLI and UI so it cannot pass for real work. A real adapter (DEC-008) plugs into the same `ModelAdapter` interface; its pricing and token estimates are still to be verified |
| DEC-018 | **Real model calls: Claude Opus 5.5 through the Messages API, under joshua's $20 monthly budget.** Real calls need a budget *and* a stored key; otherwise the simulated model runs. The key is stored encrypted by the OS (`safeStorage`, DEC-006) in its own file, never in the database or logs, and never returned to the renderer. Before each call the orchestrator reserves an upper-bound estimate (full output allowance at list price), so parallel calls cannot together pass the cap; a call abandoned at its timeout is counted at its estimate. Plans use structured outputs (JSON schema); a cut-off or declined answer fails the task and is still counted. Server-side refusal fallbacks are **not** enabled, because a fallback can run on a model with other prices and the budget check could no longer bound the cost | Adopted (joshua chose $20, 2026-10-27) | Claude Agent SDK now (DEC-008); a cheaper model; refusal fallbacks on | Plan and work calls are single requests without tools, so the Messages API is enough; the Agent SDK comes with tool execution and its sandbox. Opus 5.5 is Anthropic's recommended default; a call costs at most about $0.17. The estimate errs high, so the budget may stop slightly early. Prices are hard-coded and must be updated by hand |
